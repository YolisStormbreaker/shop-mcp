# shop-mcp: работа с сайтами магазинов

Все процессы ходят на сайты магазинов из одного Chrome и с одного IP: сервер в Claude Desktop, другие сессии, агенты, `watch.py`, разовые скрипты. Сайты отвечают на всплески проверкой на бота, а потом банят IP. 2026-11-08 Перекрёсток забанил IP пользователя на несколько часов. Причина — разбор JS-скриптов сайта подряд, два цикла проверки корзины и пять повторов в уже заблокированный сайт. Чтобы такого не было, все запросы идут через общий бюджет `pace.py`.

## Правила

1. **Ходить на сайт магазина — только через модули проекта или `cdp.Tab`.** Через `goto`, `page_json`, `capture` и функции запросов модулей. Каждый запрос там берёт слот в `pace`: паузу и место в пределах за 1, 10 и 60 минут, общих для всех процессов. Своих циклов `fetch` в странице и своих `urllib` и `curl` к доменам магазинов не пиши. Если без своего запроса не обойтись, перед каждым вызови `pace.acquire("<сайт>")` в Python или `~/shop-mcp/shop-pace wait <сайт>` в шелле.
2. **Новый сайт изучай через `netlog.py` и `bundles.py`, не повторными загрузками.**
   - `.venv/bin/python netlog.py <сайт> <url страницы>` — одна загрузка: все XHR/fetch-ответы страницы с адресами и её объекты состояния (`__NEXT_DATA__` и т. п.) ложатся в `cache/netlog/<сайт>/last.json`. Файл перезаписывается при следующем запуске: сразу копируй его под своим именем и дальше читай копию.
   - `.venv/bin/python bundles.py <сайт> <url страницы> '<regex>'` — одна загрузка, исходники всех скриптов страницы берутся из её отладчика без запросов к сети и ложатся в `cache/bundles/`.
   - Новый сайт сначала добавь в `pace.POLICY` (для неизученного — `NEW`): оба инструмента и модули не примут сайт не из бюджета.
   - Подключённый магазин внеси в `stores.STORES`: что продаёт (категории из `stores.CATEGORIES`, у маркетплейса — «всё, кроме»), в чём силён (`core`) и короткое примечание. По этой таблице агенты выбирают магазин: магазина без строки в ней для них нет.
   - В `cache/netlog/` бывают город и токен сессии: эта папка не в git, в тесты из неё ничего не переносится — только выдуманные данные (репозиторий публичный).
3. **Ответ с «⏸» означает стоп.** В нём сказано, что случилось, до какого времени и что делать. Не повторяй раньше этого времени. Не обходи остановку: другой вкладкой, другим процессом, прямым запросом, перезапуском Chrome. Займись другими магазинами и сообщи пользователю.
   - Проверку на бота проходит только пользователь: `shop-chrome show`, пройти, `shop-chrome hide`, затем `~/shop-mcp/shop-pace clear <сайт>`.
   - Блокировку по IP снимает только время. `shop-pace clear --ban` запускает только сам пользователь.
4. **Перед длинной серией запросов смотри `~/shop-mcp/shop-pace status`** или инструмент `shop_limits`. Распределяй работу по магазинам. У Перекрёстка, Пятёрочки и Самоката, которые закрыты ServicePipe, пределы самые маленькие.
5. **Живые проверки корзин и избранного — только по просьбе пользователя.** Один цикл на магазин: добавить, изменить, убрать, сверить со снимком. Если цикл прервался, сначала верни корзину, потом всё остальное. Заказы не оформлять.
6. **`pace` — только управление частотой.** Не меняй user-agent, отпечаток браузера и IP, не подключай прокси, не решай капчи, не снимай блокировки программно. Если сайт просит остановиться, мы останавливаемся.
7. **Под `python -m unittest` `pace` выключен.** Так тесты, coverage и mutator не трогают настоящий журнал `cache/pace.sqlite`. Тест не должен ходить на настоящие сайты. Тесты самого `pace` включают его со своей базой и часами.

Пределы в `pace.POLICY` — осторожные догадки по прошлым случаям, а не замеры. Каждая записанная блокировка хранит, сколько запросов было к сайту за 1, 10 и 60 минут до неё (таблица `blocks` в `cache/pace.sqlite`). По этим числам пределы и уточнять.

Остальное о разработке — в README, раздел «разработка».
